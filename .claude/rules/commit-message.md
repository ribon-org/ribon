
### Commit Message Guidelines

#### Format

コミットメッセージは絵文字 + 半角スペース + 日本語の説明で記述する

```
✨ ここにやったことの全体のまとめを記述する

- ここに詳細を記述する
```

#### 使用する絵文字

- ✨ 新規コードの追加
- 🐛 バグ修正
- ♻️ リファクタリング
- 🔥 コード/ファイルの削除
- 💄 デザイン変更
- ✅ テスト追加・更新
- 💚 CI の追加・修正
- 🔧 設定ファイルの更新
- 📦 ライブラリ/パッケージ の追加・更新・削除
- 🚚 ファイルの 移動/名前 の変更
- 🏁 Feature フラグの 追加/更新/削除
- 🚸 ユーザーエクスペリエンス/使いやすさ の向上

#### 基本原則

- **日本語で記述**: すべてのコミットメッセージは日本語で書く
- **細かくコミット**: 機能や修正を細かく分けてコミットする
- **1コミット1目的**: 1つのコミットには1つの目的のみを含める
- **変更内容を明確に**: 何を変更したかを具体的に記述する
- **使用する絵文字は1つのみ**: 1つのコミットに1つの絵文字を使用する

#### コミット時の注意事項

- **CLAUDE.mdと.env.exampleファイルは除外**: 機密情報や設定例が含まれるため、基本的にはコミット対象から除外する
- **複数コミットに分割**: 大きな変更は機能や層ごとに細かく分けて複数のコミットにする
- **論理的な順序**: 依存関係を考慮した順序でコミットする（例：スキーマ変更 → ビジネスロジック → API → UI）

#### テストと実装のコミット分割ルール

- **実装とテストは別コミット**: 実装ファイルとテストファイルは必ず別のコミットに分ける
- **ファイル単位でコミット**: 各ファイルの実装とテストをひとまとまりとしてコミットする
- **コミット順序の例**:
  1. ファイルAの実装コミット
  2. ファイルAのテストコミット
  3. ファイルBの実装コミット
  4. ファイルBのテストコミット

**具体例**:

```
✨ companiesテーブルにRLSポリシーを追加
✅ companiesテーブルのRLSポリシーのテストを追加
✨ updateCompany関数にauth0認証を追加
✅ updateCompany関数のテストを修正
```
